# Styles

Spectrum Hub combines a layered global stylesheet with unlayered block
stylesheets. This guide covers where styles belong, how to use project tokens,
and the conventions enforced by lint and review.

## Stylesheet locations

| Path | Responsibility |
| --- | --- |
| `styles/styles.css` | Fonts, generated Spectrum tokens, project tokens, global elements, layouts, utilities, and color schemes |
| `blocks/<name>/<name>.css` | Styles owned by one block |
| `deps/se/*.css` | Styles for the authored Spectrum Edge (`se-*`) components, loaded by specific features |
| `deps/swc/` | Spectrum Web Components runtime assets and generated data |

Do not add a global rule merely because several pages currently use the same
block. If a selector only makes sense inside one block, keep it with that block.

## Cascade model

Global site rules live in the `spectrum-edge` layer, opened in
[`styles/styles.css`](../styles/styles.css). Block styles declare no layer at all, and
[unlayered styles always override layered
ones](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@layer#description),
so a block rule wins however simple its selector:

```css
@layer spectrum-edge {
  /* global site rules */
}
```

Use this ordering rather than escalating specificity or adding `!important`. Note that
`!important` inverts the relationship: an important declaration inside the layer beats an
important declaration in unlayered block CSS.
When a style truly belongs globally, place it in the existing section of
`styles/styles.css` rather than creating an unrelated layer.

## Class naming

- Use kebab-case.
- Prefix child and state classes with the block name when a generic class could
  leak or collide.
- Scope all block selectors under the root block class.
- Use short variant classes on the root when their meaning is clear in context.
- Use `is-*` or `has-*` for runtime state when that reads naturally.

```css
.usage {
  .usage-panel {
    /* block-prefixed child */
  }

  .usage-panel.is-selected {
    /* runtime state */
  }
}

.card.vertical {
  /* authored root variant */
}
```

## Native nesting

Block styles use native CSS nesting. Keep the root class explicit:

```css
.example {
  display: grid;

  .example-heading {
    margin-block: 0;
  }

  &:focus-within {
    outline-color: var(--s2-blue-900);
  }
}
```

These files are delivered as browser CSS.

## Tokens

Prefer existing custom properties over literal design values. Token prefixes in
`styles/styles.css` identify their source:

| Prefix | Source |
| --- | --- |
| `--s2-*` | Spectrum 2 design tokens |
| `--se-*` | Spectrum Edge compatibility and component tokens |
| `--sh-*` | Spectrum Hub-specific tokens |
| `--swc-*` | Spectrum Web Components compatibility tokens |

The large Spectrum token region in `styles/styles.css` sits between the
`/* --- Generated by nx/deps/spectrum/build.js — do not edit --- */` and
`/* --- End generated --- */` marker comments. Do not edit values inside that range by
hand. The generator named in the marker is **not in this repository**, so there is no
local command that regenerates it. A token value that looks wrong has to be fixed
upstream. Add a project-specific `--sh-*` property only when no source token models the
concept.

## Color schemes

`styles/styles.css` sets `color-scheme: light dark` once, on `:root`, so every page that
loads it follows the visitor's preference. Many tokens then resolve through
`light-dark()`:

```css
color: light-dark(var(--s2-gray-900), var(--s2-gray-1000));
```

`section-metadata` adds `.light-scheme` or `.dark-scheme` to a section's direct children.
Those classes are more than styling hooks: `styles/styles.css` redeclares `color-scheme`
as `light` or `dark` for them, which is what makes `light-dark()` inside that subtree
resolve to the pinned scheme instead of the visitor's.

Scheme-aware media is opt-in, and authors can opt-in by providing a second picture.
`blocks/media/media.js` and `blocks/section-metadata/section-metadata.js` both guard on
`pics.length > 1` before tagging anything:

| Authored | Result |
| --- | --- |
| One picture | No classes are added. The picture is untouched and shows in both schemes |
| Two pictures | First is tagged `.scheme-aware-pic .light-pic`, second `.scheme-aware-pic .dark-pic`, and CSS shows whichever matches the active scheme |

`scripts/scripts.js` applies the same two classes to the page background, but builds
those pictures from the `light-bg` and `dark-bg` metadata keys rather than from authored
markup, so it has no picture count to guard on.

Section metadata can set a background color or image. When a color is used,
`section-metadata` calculates luminance and applies the appropriate scheme to
the section's direct content.

Test every custom color and image in both schemes. Do not infer readable
foreground contrast from the default theme.

## Responsive design

Use range media-query syntax used throughout the repository:

```css
@media (width >= 900px) {
  /* wider layout */
}
```

Prefer content-driven layouts (`grid`, `flex`, `minmax()`, wrapping) before
adding breakpoints. Keep a block's breakpoints in its own stylesheet.

Breakpoints include:

- 600px
- 900px
- 1200px
- 1800px

When a block needs to respond to its own width rather than the viewport's, use
[`@container` queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@container).

```css
@container card-container (width >= 400px) {
  /* responds to the named container width, not the viewport's */
}
```

## Motion

Animation and transitions must respect the user's motion preference:

```css
@media (prefers-reduced-motion: reduce) {
  .example {
    transition: none;
  }
}
```

Motion should communicate state, and not be required to understand or operate the
interface.

## Layout and section metadata

Authors can apply section-level values through the `section-metadata` block:

| Key | Runtime result |
| --- | --- |
| `style` | Adds normalized classes to the section |
| `grid` | Adds `grid` and `grid-<value>` |
| `gap` | Adds `gap-<value>` |
| `radius` | Adds `radius-<value>` |
| `spacing` | Adds `spacing-<value>` |
| `container` | Adds `container-<value>` |
| `layout` | Adds `layout-<value>` |
| `background`, `background-color`, `background-image` | Applies a color or scheme-aware background media |

Before adding a new authored style variant, check whether an existing global
layout or section-metadata value already expresses it.

## Accessibility

- Preserve visible focus indicators.
- Use actual disabled/inert semantics; do not communicate state only by color.
- Maintain WCAG 2.2 AA contrast in both schemes.
- Avoid fixed heights that clip enlarged text.
- Let text wrap and layouts reflow at narrow widths and high zoom.
- Hide decorative icons from assistive technology in markup rather than with visual CSS alone.

Every block has an axe scan and accessibility-tree snapshot under `test/a11y/`.
Style changes can alter visibility and accessible names, so run the relevant
spec even when JavaScript did not change.

## Linting

Run:

```bash
npm run lint:css
```

[`.stylelintrc.json`](../.stylelintrc.json) extends `stylelint-config-standard` and
changes two rules: `no-descending-specificity` is disabled, because layered globals and
nested block styling can require it, and `property-no-vendor-prefix` rejects vendor
prefixes except `-webkit-backdrop-filter`. Note that `lint:css` covers
`blocks/**/*.css` and `styles/*.css` only — stylesheets under `deps/` are not linted.

## Review checklist

1. The selector belongs in the chosen global or block stylesheet.
2. Child classes are block-scoped kebab-case, not BEM.
3. Existing tokens replace unexplained literal colors, spacing, and type values.
4. Light and dark schemes both work.
5. Narrow widths, zoom, long text, and reduced motion work.
6. `npm run lint:css` passes.
7. The affected accessibility spec passes.
